## W1 — Why 6 tasks / ~28 files are NOT being split

The checker raised splitting 06-01 into a/b/c/d. After review, the plan stays consolidated. Justification:

- The six tasks are a tightly coupled foundational layer: domain models -> Room schema -> repository impl -> Cloud Functions -> security rules. Splitting them creates compile-time circular dependencies (e.g., OrderRepositoryImpl in `:data` cannot compile without the SellerOrder domain model; rules tests need both rules and the fan-out batch shape; the Room migration verification needs the entity).
- Test scaffolds (Task 0) are the only piece that could move, but moving them defeats their purpose — they exist to give Tasks 1-5 something to flesh out without recreating boilerplate.
- Total files modified (~28) is high but driven by breadth, not depth: each file averages a small focused change (one entity, one DAO, one mapper, one migration). No single file gets >120 LOC of new code.
- All six tasks compile and are testable independently within the same plan (each task has its own `<verify>` block).
- 06-02, 06-03, 06-04 already split off the consumer concerns (UI + FCM); 06-01 is the irreducible foundation.

If the executor finds context pressure during execution, the cleanest split is to extract Task 4 (Cloud Functions) and Task 5 (rules + emulator tests) into a 06-01b — a graceful escape hatch — but the planner judges the cohesion benefit outweighs the split.

## W2 — No inline code dumps

Implementation details (Kotlin data class bodies, jest configs, full Cloud Function TypeScript) live in RESEARCH.md sections (§2.1, §2.2, §2.3, §2.6, §2.8, §3). Tasks below reference those sections by anchor and list fields/identifiers/imports — not full code blocks.

## W6 — D7 amendment (JSON-columns vs @Relation)

CONTEXT D7 originally said "new Room entities ... with a `@Relation` for one-to-many fetching." Per RESEARCH §2.5 the implementation substitutes JSON columns on `SellerOrderEntity` (itemsJson, statusHistoryJson) following the established `OrderEntity.itemsJson` pattern from Phases 4-5. Bounded sizes (≤5 status entries, ≤~20 items) keep this lossless and fast; `@Relation` would add boilerplate (`@Transaction` wrappers or manual stitching) for no measurable benefit. The one-to-many parent->subs fetch is handled by a separate DAO query (`SellerOrderDao.observeByParent`) and assembled in `OrderRepositoryImpl.observeOrderWithSubOrders` via `combine`. The CONTEXT amendment is recorded in `06-CONTEXT.md` under `<decisions>` as the 2026-06-16 amendment.
