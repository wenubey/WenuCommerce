Build the server + data foundation for reviews. This is the critical-path blocker: every UI plan (07-02, 07-03) reads from the Room `ReviewEntity` and depends on the `submitReview` callable maintaining the product-doc aggregate.

Establish a server-authoritative write path — the `submitReview` and `markReviewHelpful` Cloud Functions become the ONLY way review docs and rating aggregates change (D-01/D-02/D-04). The offline write queue's `SUBMIT_REVIEW` TODO is wired.

Purpose: Reviews cannot be spoofed, double-submitted, or vote-stuffed, and the aggregate cannot be tampered with client-side. This satisfies the review-integrity threat model.
Output: submitReview + markReviewHelpful callables, tightened rules + merged index, ReviewEntity/DAO/Mapper + MIGRATION_8_9, re-routed repository, wired SyncWorker.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Android client → Firestore (direct) | Untrusted — any authed user could previously write review docs and rating fields |
| Android client → Cloud Function (callable) | request.auth verified; server owns all review + aggregate mutations |
| Cloud Function → Firestore (Admin SDK) | Trusted — bypasses rules; the sole write path for reviews/votes/aggregates |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Spoofing | Fake "Verified Purchase" review with no delivered order | mitigate | submitReview queries sellerOrders (userId==uid, status==DELIVERED, productId in items[]) server-side; rejects with failed-precondition; isVerifiedPurchase set only by the function (Task 1) |
| T-07-02 | Tampering | Client writes/edits/deletes a review doc directly | mitigate | Firestore rules: `REVIEWS/{reviewId}` create/update/delete = false; verified by rules Jest assertFails cases (Task 2) |
| T-07-03 | Tampering | Client manipulates ratingAverage/reviewCount on product doc | mitigate | Aggregate recomputed only inside the submitReview Admin-SDK transaction; product-doc rating fields written server-only (Task 1). NOTE: top-level product doc write stays client-allowed for seller product mgmt (A1); the aggregate is protected because clients have no reason/path to set it and any client set would be overwritten on next server recompute. Residual risk accepted — low (no incentive to poison own product; seller owns product). |
| T-07-04 | Tampering | Helpful-vote ballot-stuffing (one user votes many times) | mitigate | markReviewHelpful transaction checks helpfulVotes/{uid} existence → already-exists on repeat; helpfulVotes writes server-only in rules (Tasks 1, 2) |
| T-07-05 | Elevation of Privilege | Duplicate reviews inflating count | mitigate | One-per-(reviewer,product) enforced in the function; edit replaces in place, count unchanged (Task 1) |
| T-07-06 | Denial of Service | Review bombing via rapid submissions | accept | Idempotent replace (second submit overwrites, does not accumulate); Firebase per-callable rate limits apply. No custom throttle this phase — low value target. |
| T-07-07 | Information Disclosure | Reading other users' reviews | accept | Reviews are public product content by design; reads open to authenticated users (D-02) |
| T-07-SC | Tampering | npm installs in functions/ | mitigate | No new packages in Phase 7 (RESEARCH: "No new packages installed"). No install task; T-07-SC dispositioned as not-applicable/accept. |
