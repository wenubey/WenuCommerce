<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Android client → Firestore | Follow/unfollow writes cross from the (authenticated) client into Firestore subcollection `USERS/{uid}/followed_sellers/{sellerId}` |
| Android client → Room | Local persistence; source of truth, no external trust concern but must never write `followerCount` anywhere |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Tampering | FollowedSellersRepositoryImpl / any client write | mitigate | Repository writes ONLY the follow doc body (sellerId/sellerName/sellerLogoUrl/followedAt); it NEVER writes `followerCount`. Counter is Admin-SDK-only (enforced by the Cloud Function in 09-02). Acceptance grep confirms no `followerCount` write in the repo impl. |
| T-09-02 | Elevation | followSeller called with blank/anonymous userId | mitigate | Repository has NO anonymous branch (D-03); the auth guard lives in the ViewModel (09-03). Interface signature requires a non-null `userId: String`. |
| T-09-03 | Info Disclosure | followed_sellers subcollection location | mitigate | Structural: follow docs are written under the CUSTOMER's own space (`USERS/{userId}/followed_sellers/...`), never the seller's — the seller cannot enumerate followers (FAVS-04). Firestore rule enforcement is added in 09-02. |
| T-09-04 | Tampering | Firestore write failure leaving inconsistent state | accept | Fire-and-forget (CD-02): Room stays authoritative; a swallowed Firestore failure is logged (Timber) and reconciled on next successful write. Acceptable for read-heavy social data. |
| T-09-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages installed in this plan (09-RESEARCH.md Package Legitimacy Audit: none). No install task present. |
</threat_model>
